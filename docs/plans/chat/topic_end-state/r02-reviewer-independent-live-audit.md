## Executive finding

The accepted end-state is still necessary: libghostty-vt must become the only
VT parser and semantic authority, while the frontend becomes a presentation
surface over an ordered renderer-independent model.

The enablers materially reduced implementation risk, but they did not move the
production authority boundary. The live path is still dual-VT:

```text
PTY bytes
  -> RuntimeActor::handle_output
  -> VtReplayEngine::feed (Ghostty parses)
  -> TerminalEvent::Output / TerminalEvent::Replay
  -> Tauri JSON byte arrays or control-socket base64
  -> TerminalAttachmentController
  -> terminalOutputQueue
  -> xterm.write / term.reset (xterm parses again)
```

`RuntimeActor` still owns `vt: VtReplayEngine`
(`core/backend/src/terminal/runtime.rs:287-305`), output still publishes the
original PTY bytes after feeding Ghostty (`runtime.rs:762-775`), and resize and
theme changes still reconstruct an ANSI replay (`runtime.rs:646-725`). The
replay itself is generated by formatting Ghostty state back into VT sequences
(`core/backend/src/terminal/replay.rs:119-145,233-273`).

## What the original closure still requires

### 1. Production host semantics

Replace `VtReplayEngine`'s ANSI formatter role with an owned semantic projector
over active screen and retained history. It must expose cells, rows, cursor,
modes, palette/defaults, hyperlinks, prompt metadata, dirty regions, and
ordered terminal effects. The test-only input and selection probes must become
production commands, and the OSC 9 gap plus the unproven gesture/autoscroll
selection behavior must be resolved explicitly.

### 2. A semantic protocol across every adapter

Define versioned snapshots and deltas with state revision, base revision,
geometry, history-window semantics, ordered effects, and recovery boundaries.
Then replace raw/replay payloads in all transports:

- Tauri currently accepts `Channel<TerminalEvent>`
  (`core/backend/src/terminal/commands.rs:90-105`), the client receives
  `Channel<unknown>`, and input is a JSON decimal array
  (`core/frontend/platform/tauri.ts:220-243`).
- The instance protocol still defines replay and output as base64 VT bytes
  (`core/backend/src/instance/protocol.rs:318-359`), and its adapter encodes
  both raw variants (`core/backend/src/instance/control.rs:1072-1108`).
- CLI raw attach writes decoded replay/output bytes directly to stdout
  (`cli/src/terminals.rs:249-363`).

The transport choice remains measurement-gated; “raw Tauri channel” is a
candidate, not a conclusion that should be frozen before the benchmark.

### 3. Canonical client model and continuous attachment

Evolve the controller seam to own a renderer-independent cell/history model,
revision checks, viewport state, explicit history requests, effect dispatch,
and bounded recovery. Hidden tabs must remain attached and keep applying model
updates. Today the view refuses to attach while hidden and disposes the
controller when `visible` changes (`core/frontend/terminal/TerminalView.tsx:226-247,418-430`).

### 4. Presentation-only surface with capability parity

Replace xterm-owned parsing, input encoding, selection, link detection,
measurement, and rendering with a surface that consumes only the client model.
The current view still owns `term.onData`, bell, OSC 9, custom key handling,
and xterm addons (`TerminalView.tsx:90-159`); reset/replay is installed directly
into xterm (`TerminalView.tsx:243-270`); and even geometry measurement creates a
hidden xterm plus `FitAddon` (`core/frontend/terminal/terminalMeasure.ts:1-45`).
Five xterm packages remain in `package.json:30-34`, with imports spread across
eight terminal modules.

### 5. Global cutover, deletion, and permanent conformance

Run the new model behind an explicit migration boundary, cut every production
consumer together, then delete `Output`, ANSI `Replay`, `VtReplayEngine`, xterm,
its addons, the byte output queue, and raw/base64 terminal adapters. Install a
negative dependency gate and packaged-app conformance scenarios so the second
parser and raw terminal byte streams cannot return.

## Recommended five delivery areas

These are implementation seams, not a status overlay:

1. **Host semantic state, ordered effects, and semantic input become
   production.** Own the projection and close parser API gaps here. Do not put
   wire delta/baseline behavior in this area.
2. **A versioned, measured semantic protocol replaces raw VT at every
   adapter.** Own snapshot/delta/history schemas, revisions, recovery contracts,
   Tauri/control/CLI encoding, benchmarks, and the migration switch here.
3. **The attachment owns the canonical client cell/history model and remains
   continuous.** Own model application, viewport state, effect delivery,
   sequence/revision recovery, and hidden-tab behavior here.
4. **A presentation-only surface reaches explicit capability parity.** Own
   geometry, rendering, input gestures, selection, links, IME, accessibility,
   theme/font behavior, and performance here.
5. **The single-VT cutover deletes every duplicate authority and makes the
   boundary permanent.** Own final rollout, legacy deletion, dependency bans,
   conformance traces, soak, and rollback evidence here.

The technical dependency is 1 -> 2 -> 3 -> 4 -> 5. Capability inventory and
acceptance scenarios for area 4 should begin in parallel with area 1 because
they can falsify the surface choice early; they are a gating subtrack of area 4,
not a sixth area and not a substitute for a production architecture seam.

## Challenges to round 01 and Claude round 1

1. Round 01's “compatibility/retention evidence only” description understates
   the completed preparation. The legacy contract gate, attachment controller,
   and single-writer registry/input seam are also live. Its conclusion that the
   production authority boundary is unchanged is correct.
2. Calling original closure area 01 “roughly half done” is too generous if its
   own acceptance criteria are the denominator. Feasibility and retention are
   materially complete, but production projection, dirty invalidation,
   production effects/input, OSC 9, and the full gesture selection machine are
   still absent.
3. `Host projection and delta contract` should not be one area. Projection is
   the owned domain read model; delta baselines, subscriber revision, wire
   recovery, and history requests are protocol/transport concerns. Mixing them
   obscures ownership and makes areas 01 and 02 impossible to validate alone.
4. The capability bill should be front-loaded, but it should not consume one of
   the five highest-value implementation areas. Put the acceptance register and
   representative conformance fixtures inside the presentation-surface area and
   start that discovery subtrack immediately. Otherwise transport, surface
   implementation, and global deletion become artificially overloaded.
5. `Surface cutover and permanent conformance` is also too broad as one area.
   Building a parity-complete presentation surface and deleting every legacy
   protocol/parser path have different blast radii and rollback boundaries; keep
   them as areas 04 and 05.
