# Fork release identity and update channel

## Purpose

Cut this fork's dependency on upstream's release infrastructure by taking
ownership of the updater signing key, the release channel, and the app's install
and product identity — so that upstream can no longer install code on our users'
machines, and we can.

## Expected Outcomes

- The app's updater trusts a minisign key held by this repository's owner.
- An artifact signed by upstream's key is demonstrably rejected.
- Update metadata and artifacts are published to and consumed from
  `ddebowczyk/shep`.
- The app installs as `shipctl.app` under `com.cognesy.shipctl` and can coexist
  with any `shep.app` build.
- No user-visible surface says "Shep".
- `~/.shep/` and `<repo>/.shep/workspace.yml` are untouched, and existing usage
  history, assistant sessions, and project configuration survive intact.
- `scripts/release-build.sh` runs end to end and produces correctly named,
  signed, notarized artifacts.

## Owner gate

The updater keypair (W1) must be generated by the repository owner on the
owner's machine. It must not be produced by an agent, committed, pasted into a
transcript, or stored in CI. Its private half is backed up off-machine before
any release is cut.

This step is a one-way door: once a build carrying the new `pubkey` is
distributed, installs carrying the old key can never be updated by us, only
replaced by hand. Rollback after distribution costs the same as rolling forward.

## Candidate work packages

Rewrite these against live code before creating issues. They are scoped from a
snapshot, not from the current tree.

1. **W1 — Trust root.** Generate the keypair, restore `.env`, install the public
   key into `tauri.conf.json`. Owner only. Blocks W3.
2. **W2 — Configuration, artifact paths, and strings.** Identifier, product
   name, endpoint, release URLs, the four build scripts, user-visible copy, and
   the comment recording why `.shep` data paths are deliberately unchanged.
   Blocks W3.
3. **W3 — First release.** Version bump, signed and notarized build, GitHub
   release on the fork. Depends on W1 and W2.
4. **W4 — Retire the exposed install.** Independent; can start immediately.
   Decline upstream's 0.6.0 prompt until `shipctl` is installed, then remove
   `shep.app` and its identifier-scoped residue.
5. **W5 — Verification.** V1–V8 in the execution guide. Depends on W3.

## Out of scope

- Internal crate, package, and workspace-alias renames (`shep-core`,
  `tauri-plugin-shep-*`, `@shep/*`). Deferred until the module boundaries
  settle; they are invisible to users and collide with in-flight refactor work.
- Renaming any on-disk path: `~/.shep/`, `<repo>/.shep/workspace.yml`,
  `.shep-worktrees/`. These are a compatibility contract, and
  `<repo>/.shep/workspace.yml` is committed inside users' own repositories. A
  rename would be a versioned migration with its own plan, not a branding change.
- CI/CD release automation.
- Multi-platform updater support beyond `darwin-aarch64`.
- Changes to `research/**`, which documents the upstream remote deliberately.

## Definition of done

All acceptance criteria in the plan README hold, with V2 (upstream-signed
artifact rejected) demonstrated rather than assumed, and V6 (existing `~/.shep/`
data read intact by the renamed app) confirmed against real data.
