# Target design and trust model

## The trust model we are moving to

An auto-updater is a remote code execution channel with one gate: the signature
check. The design question is not "where do we download from" but "whose
signature is sufficient to run code on our users' machines."

| | Today | Target |
|---|---|---|
| Trust root | upstream's minisign key | a key we hold |
| Distribution | `stumptowndoug/shep` releases | `ddebowczyk/shep` releases |
| Install identity | `com.shep.terminal` (shared) | `com.cognesy.shipctl` (ours) |
| Can upstream push code to us? | **yes** | no |
| Can we push code to our users? | **no** | yes |

Both rows in the bottom half flip on the `pubkey` line alone. The endpoint
determines availability; the key determines authority. They change together
because changing either alone yields a broken state: a new key with the old
endpoint finds only artifacts it rejects, and a new endpoint with the old key
serves only artifacts we cannot sign.

## Design decisions

### D1 — Keys are generated by the owner, on the owner's machine

`pnpm tauri signer generate` produces a minisign keypair. The private half is
stored outside the repository and referenced through
`TAURI_SIGNING_PRIVATE_KEY_PATH` in `.env`, matching the mechanism
`release-build.sh` already expects. No new secret-handling machinery is
introduced.

An agent must not generate this key, and CI must not hold it. There is no CI
today; if release automation is added later, that is a separate decision with
its own threat model.

### D2 — Distribution stays on GitHub Releases

The fork repository is public, `release-build.sh` already ends in
`gh release create`, and the CSP already allows the required hosts. This is the
smallest change that reaches the target trust model.

The accepted cost: the repository must remain public, because the updater
authenticates nothing. If the repository ever needs to go private, distribution
must move to a static host and `connect-src` must be widened — a change this
plan deliberately does not pre-build for.

### D3 — Identifier `com.cognesy.shipctl`, product `shipctl`

Taking a distinct identifier means a fork build and an upstream build can coexist
on one machine and can never overwrite each other. It also means the first
`shipctl` release lands beside the exposed `shep.app` rather than needing it
removed first.

The cost is bounded to WebView-local UI preferences (theme, panel layout,
sidebar state) under `~/Library/WebKit/com.shep.terminal` and friends.
`~/Library/Application Support/com.shep.terminal` is empty. No migration code is
warranted for a one-minute re-set of visual preferences.

### D4 — The data contract keeps the `.shep` name

`~/.shep/` and `<repo>/.shep/workspace.yml` are **not** renamed. Three reasons,
in order of weight:

1. `<repo>/.shep/workspace.yml` is written into users' project repositories and
   is normally committed. It is an interoperability contract with existing
   checkouts. Renaming it silently invalidates every configured project.
2. `~/.shep/usage.sqlite3` is 43 MB of accumulated history with no rebuild path.
3. `.shep-worktrees/` appears in user gitignore files we do not control.

A product rename is cosmetic; a data-path rename is a migration. Coupling them
would convert a safe change into a data-loss risk for no user-visible gain. If a
rename is wanted later it needs dual-path reads, a versioned migration, and a
rollback story — its own plan.

This asymmetry should be stated in the code so it does not read as an oversight:
a short comment at `core/backend/src/workspace/loader.rs` recording that `.shep`
is a stability contract, not stale branding.

### D5 — Internal namespaces are not renamed now

Crate names, the `@shep/*` workspace scope, and the Rust binary name are
invisible to users. Renaming them means editing every `Cargo.toml`, every module
import, and the alias contract in `core/frontend/README.md` — the same files the
modular-monolith refactor is actively moving. Deferred as mechanical follow-up.

Note that `productName` and the Cargo binary name are independent in Tauri: the
bundle can be `shipctl.app` while the crate stays `shep`. `build-local.sh:105`
hashes `Contents/MacOS/shep`, so the executable name must be verified against
the actual build output rather than assumed either way.

### D6 — Single-platform scope preserved

`latest.json` continues to describe only `darwin-aarch64`. Widening the platform
matrix is unrelated to cutting the upstream tie.

## Target configuration

`src-tauri/tauri.conf.json`:

```json
{
  "productName": "shipctl",
  "identifier": "com.cognesy.shipctl",
  "app": { "windows": [{ "title": "Shipctl" }] },
  "plugins": {
    "updater": {
      "endpoints": [
        "https://github.com/ddebowczyk/shep/releases/latest/download/latest.json"
      ],
      "pubkey": "<contents of the generated .key.pub>"
    }
  }
}
```

CSP is unchanged.

## Failure modes this design accepts

| Mode | Consequence | Mitigation |
|---|---|---|
| Old installs keep upstream's key | They can still be updated *by upstream* | Identifier change means the new build installs beside them; retire old installs manually |
| Fork private key lost | No future updates installable; every user reinstalls manually | Owner backs up the key file off-machine |
| Fork repo made private | Updater 404s silently | Repo stays public, or distribution moves (D2) |
| `latest.json` published without matching assets | `check()` reports an update that fails to download | Verification step V4 |

## Explicit non-goals

- No CI/CD release automation.
- No multi-platform updater matrix.
- No staged rollouts, channels, or update gating.
- No data migration of any kind.
- No internal crate or package renames.
- No changes to `research/**`, which documents the upstream remote on purpose.
