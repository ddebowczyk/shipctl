# Performance insights: what the semantic path costs

Measured 2026-08-11 on darwin 25.6.0, Apple silicon, release build. Evidence and
raw table: `research/notes/terminal-semantic-path-profile-20260811-1053.md`.
Harness: `core/backend/src/terminal/measure.rs` (test-only, ignored by default).

This is a diagnosis, not a gate. No product requirement or technical contract in
this repository sets a frame or throughput budget for a terminal, so no number
here is a threshold and none should become one without an owner saying so.

## The question

The byte path sent the child's bytes. The semantic path sends state: every
occurrence makes the host project its whole screen and encode that projection
for each client. The webview builds the semantic surface now
(`WEBVIEW_TERMINAL_TRANSPORT = "semantic"`), so this cost is the product's cost.
Area 05 deletes the alternative, and after that there is no cheaper path to fall
back to. The trade had to be measured before then.

## How it was measured

The harness does what `RuntimeActor` does per PTY read: feed one 4 KiB chunk
(`PTY_READ_CHUNK_BYTES`), project, encode. No process and no window, so the
numbers are the host's own cost. The client half — `JSON.parse` plus
`decodeScreenState` — was measured over the same shape in bare node, 200 runs
per geometry.

Workloads: 2 000 lines of plain output (the same workload the
`measure.sustained-output` scenario writes), the same lines with SGR colour, and
2 000 full-screen repaints. Geometries 80x24 (the PTY's own default), 120x40 and
200x50 are sampled points, not targets: the product's geometry is whatever the
person's window is.

## What one frame costs

| geometry | project | encode | host per frame | JSON per frame | client parse+decode |
| --- | --- | --- | --- | --- | --- |
| 80x24 | 181 µs | 150 µs | 0.33 ms | 185 KB (96 B/cell) | 0.53 ms |
| 120x40 | 422 µs | 338 µs | 0.76 ms | 461 KB (95 B/cell) | 1.28 ms |
| 200x50 | 629 µs | 687 µs | 1.32 ms | 956 KB (95 B/cell) | 2.57 ms |

Colour and full-screen repaints move these by less than a tenth. The cost
follows the cell count, not the content.

## The diagnosis

**The CPU is affordable. The wire is not.**

One frame of an 80x24 terminal is 185 KB of JSON; one of a 200x50 terminal is
956 KB. That is about 96 bytes per cell, and a cell is usually one ASCII
character. The host publishes one such frame per 4 KiB PTY read, so a program
writing quickly turns a 4 KiB read into a 185 KB–956 KB message that crosses
IPC, then is parsed and validated on the client: 0.9 ms to 3.9 ms of combined
CPU per frame, and hundreds of megabytes per second of traffic if the reader
keeps up.

Two remedies were measured against that. Only one of them helps.

### Sending only the damaged rows buys nothing

The host's damage report is honest, and under scrolling output every row
genuinely changes: 24.0 of 24 rows per frame at 80x24, 50.0 of 50 at 200x50.
Encoding only the damaged rows saves under 1 % on this workload. The obvious fix
is the wrong fix.

### Carrying runs instead of cells buys nearly everything

Adjacent cells that share style, width, selection and hyperlink differ only in
their text. `terminalCellPaint.ts` already rebuilds exactly those runs before it
paints, so the run-break rule exists on both sides already. Encoding the frame
that way, with that same rule:

| geometry | cell per cell | as runs | ratio |
| --- | --- | --- | --- |
| 80x24 | 185 KB | 3.2 KB | 57× |
| 120x40 | 461 KB | 5.5 KB | 84× |
| 200x50 | 956 KB | 6.8 KB | 140× |

Styled output — the unfriendly case for runs — still gives 11.5 KB at 80x24 and
24 KB at 200x50: 17× and 40×.

## What this means for the five areas

Neither change is needed for the product to work today at ordinary output rates.
Both belong before area 05 deletes the byte path.

1. **Carry runs on the wire (area 02).** The information is identical and the
   run-break rule already exists on both sides. It changes the protocol and its
   checked-in fixtures — `terminalScreenFixture.json` and the event contract —
   not the client model and not the presentation surface. Owner decision,
   because it changes a contract already accepted.
2. **Publish per reader, not per read (area 01).** The runtime publishes on
   every PTY chunk; the client paints once per animation frame and coalesces the
   rest. A host that publishes the state a reader has not yet taken, rather than
   one per read, would drop the frame count with no chosen interval and no
   invented rate — self-clocking, which is the only form this repository's rules
   allow.
3. **Area 05 should not delete the byte path until both land**, because the
   deletion removes the fallback that makes a wire-size mistake survivable.

## Still to measure

The mounted half: IPC transfer time and paint time in the packaged app. The
scenario harness reports it — `globalThis.__shipctlTerminalScenarios.run(<terminalId>)`
— and the probe drives the semantic surface now, so `output.rate`,
`frames.mean`, `frames.slowest` and `resize.round-trip` describe the path that
ships. `measure.sustained-output` and `renderer.gpu-loss-fallback` stay blocking
in the capability register until those numbers are recorded.

## Reproducing

```text
cargo test -p shipctl-core --lib --release terminal::measure -- --ignored --nocapture
```

`--release`, because a debug build measures the compiler rather than the design.
