# Remaining work to the single-VT end state

Recorded 2026-08-11. A snapshot of the working tree against the five areas, not
a plan revision: the areas keep their acceptance criteria, and this says how
much of each is already standing.

Read it with a date in mind. The tree moved during the session that produced
this — `TerminalEvent::Screen`, `effects.rs`, `painter.rs` and the
`TerminalTransport` switch all landed while it was being written. Verify before
acting on any single line.

## Where it stands

`TerminalTransport { Legacy, Semantic }` (`core/backend/src/terminal/types.rs`)
is the migration switch area 05 owns, selected per attachment.
`EventAudience` (`core/backend/src/terminal/publication.rs`) keeps the two
encodings disjoint, so one occurrence produces at most one event per audience
and either stream stays consecutive.

Three clients, three states:

- **CLI** — selectable with `--encoding semantic`, and done.
  `painter::paint(projection)` and `paint_effects` in `cli/src/terminals.rs`.
- **Control socket** — passes the encoding through, and done.
  `attach_with(id, sink, false, encoding)` in
  `core/backend/src/instance/control.rs`.
- **Webview** — hardcoded `Legacy`. `commands.rs::attach_terminal` calls
  `attach()` and never `attach_with()`.

Area 04's CLI half is finished and proved against fixtures the host's own
parser wrote. What remains is the webview half and the deletions.

## TypeScript

`terminalCellPresenter.ts` and `terminalCanvasTarget.ts` have no production

## What this means for the schedule

Rust is close. A signature change and one service method, then deletions.

TypeScript is not close in the same way, but the remaining work is unusually
well shaped. `terminalClientModel.ts`, `terminalCellPaint.ts`,
`terminalSemanticInput.ts`, `terminalCellPresenter.ts`,
`terminalCanvasTarget.ts` and `terminalCellSurface.ts` all exist with tests,
decoding a fixture the host's own parser wrote. What is missing is the surface
that binds them and the font-metrics probe: two modules, both small, both
blocking everything downstream.

Two things that should keep the estimate honest.

**The register reports 19 of 47 capabilities blocking.** Most are blocking only
because no mounted webview surface exists to prove them against, and would flip
in a batch once `terminalSemanticSurface.ts` lands and the scenarios run. Four
are not paperwork: `input.ime`, `unicode.glyph-fits-span`, `a11y.keyboard-focus`
and `input.mouse-reporting` are where a semantic surface historically loses to
xterm, and they will not resolve on a schedule.

**Nothing has run the two paths side by side on a real terminal.** Every proof
so far is a fixture, a trace, or the CLI. The first time a shell running a
full-screen program is driven through the webview semantic path is the first
real test of frame rate and damage granularity, which is why
`measure.sustained-output` is in the blocking list. Do not compress the schedule
on the assumption that it lands clean.

## Alternatives considered and not taken

Recorded so the question is not reopened without new facts. Researched
2026-08-11 against crates.io and GitHub.

No library supplies the thing this plan is actually building. PTY spawning is
solved many times over (`portable-pty`, `pty-process`, `teletypewriter`), and a
host VT with full semantic state is solved (libghostty, `alacritty_terminal`,
`rio-vt`, `avt`, `vt100`). A serialized semantic protocol from a Rust host to a
non-Rust client does not exist as a library: every Rust terminal engine assumes
the renderer is Rust and in-process.

The one precedent is **wezterm's mux codec**, which validates this design almost
point for point — `StableRowIndex` is an anchor, `seqno` is a sequence,
`dirty_lines: Vec<Range<StableRowIndex>>` is committed damage, and
`SerializedLines` decomposes `Arc<Hyperlink>` into a side table to preserve cell
identity across the wire. Worth reading before the wire format is frozen. It is
bincode between two Rust processes, `wezterm-term` is not published to
crates.io, and it does not help a TypeScript client.

Two findings that were weighed and set aside, both worth revisiting if the
schedule slips:

- **libghostty-vt has an official WASM target** (`include/ghostty/vt/wasm.h`,
  `zig build -Demit-lib-vt -Dtarget=wasm32-freestanding`, with `example/wasm-vt`
  and `example/wasm-key-encode`). Running the same parser in the webview would
  make occupancy agree by construction rather than by protocol. It does not
  deliver one VT authority, which is what these areas are for, and the mature
  consumer (`restty`, MIT, on npm) is early-release software built against a
  personal fork of ghostty that already trails upstream.
- **A snapshot format landed upstream on 2026-08-03** (`GHOSTSNP`, versioned and
  CRC-protected, carrying scrollback pages and unfinished parser input, with a
  `READY` marker and incremental history prepending). That is five days after
  the revision pinned in `core/backend/Cargo.toml`, and `libghostty-rs` has not
  wrapped it. If it holds up it could replace the ANSI reconstruction in
  `replay.rs` with a state handoff. Worth a look during the area-05 upgrade,
  independently of the WASM question.

Also noted: `include/ghostty/vt/render.h` is a stateful, dirty-region render
state API from the parser's own authors, designed so a renderer reads frame data
without holding the terminal lock. It covers ground `publication.rs` covers by
hand.
